# 개발 로그 — AI 에이전트와 일한 과정

원본 저장소의 이슈·PR 흐름을 이 저장소용으로 정리한 기록입니다(저장소를 새로 만들어 PR 페이지는 옮길 수 없었습니다). 각 항목은 **무슨 일이 있었고, 에이전트가 무엇을 했고, 제가 무엇을 판단·검증했는지**를 적었습니다. 작업 규칙은 [`AGENTS.md`](../AGENTS.md)에 있습니다.

공통 원칙: 에이전트가 변경 요약을 주면 제가 승인한 뒤에만 코드를 고쳤고, git 작업(커밋·브랜치·PR)은 제가 직접 했습니다. 에이전트 환경에서는 Gradle·Docker를 돌릴 수 없어 백엔드 테스트는 제가 실행했습니다.

---

## 1. 좋아요 동시성: CI 간헐 실패

- **상황**: 같은 사용자가 좋아요를 연타하면 CI에서 간헐적으로 테스트가 실패했습니다.
- **원인**: 유일 제약 + 재시도만으로 토글을 처리해서, "삽입 → 삭제" 두 단계 사이에 다른 요청이 끼어들 수 있었고 재시도 횟수를 넘기면 클릭이 반영되지 않았습니다.
- **해결**: (글, 사용자) 단위 `pg_advisory_xact_lock`으로 같은 사용자의 요청을 한 줄로 세우고, 카운트는 `UPDATE ... RETURNING`으로 원자적으로 갱신했습니다. 설계 근거는 [`readme-decisions.md` A6](./readme-decisions.md).
- **역할**: 실패 로그와 설계 대안(낙관적 락, `SELECT FOR UPDATE`, 유일 제약 + 재시도)을 비교하고 선택한 것은 제 판단이었고, 에이전트는 대안별 실패 시나리오 분석과 재현 테스트 작성을 도왔습니다.

## 2. 글 삭제 중 댓글 작성: "막혀 있는가, 테스트만 없는가"

- **상황**: 외부 리뷰에서 "글 삭제 중 댓글 작성" 경합이 테스트되지 않았다는 지적이 왔습니다. 저는 설계가 막고 있는지, 테스트만 빠진 건지 에이전트에게 검토를 요청했습니다.
- **에이전트가 한 일**: 코드를 읽어 **실제로 막혀 있지 않다**는 것을 확인했습니다. 삭제는 soft delete(UPDATE)라 FK가 막아 주지 않고, "글이 살아 있는지 확인(일반 SELECT) → INSERT" 사이에 삭제가 커밋되면 삭제된 글에 댓글이 생기고 201이 나갔습니다.
- **해결**: 댓글 작성은 글 행을 `FOR KEY SHARE`, 삭제는 `FOR UPDATE`로 잡아 서로 충돌하게 했습니다. `FOR SHARE`는 `like_count` UPDATE와 충돌하므로 쓰지 않았습니다(이 판단은 PostgreSQL 락 충돌 표를 같이 확인하며 정했습니다). 좋아요는 `UPDATE ... WHERE deleted_at IS NULL`이 삭제의 행 락을 기다린 뒤 조건을 다시 평가하므로 별도 락 없이 이미 안전했고, 이를 테스트로 확인했습니다.
- **테스트 방식 결정**: `sleep` 기반 타이밍 대신, 별도 커넥션이 락을 쥔 채 대기하는 `LockProbe`와 `pg_stat_activity`의 `Lock` 대기 폴링으로 결정적으로 만들기로 했습니다. 에이전트가 두 방식의 장단점을 제시했고 폴링은 제가 결정했습니다.
- **후속 발견**: 같은 방식으로 훑다가 **수정(UPDATE)과 삭제의 경합**도 확인했습니다. 수정의 UPDATE가 `deleted_at`까지 덮어써 삭제된 글이 되살아날 수 있었고, 수정은 `FOR NO KEY UPDATE`로 잡도록 고쳐 별도 PR로 나눴습니다.
- **정리**: [`readme-decisions.md` A8](./readme-decisions.md), README "정합성과 동시성".

## 3. 댓글 "더보기" 버튼이 뒤로가기 후 다시 보이는 문제

- **상황**: 댓글 2개 → "더보기" 클릭 → 스크롤하며 읽다가 뒤로가기 후 앞으로 가기로 글에 돌아오면, 이미 불러온 댓글이 있는데도 "더보기" 버튼이 다시 보였습니다. 스크롤 위치가 복원되는 동작은 유지하고 싶었습니다.
- **원인(에이전트 분석)**: "더보기를 눌렀는가"를 컴포넌트의 `useState`로 들고 있어서, 컴포넌트가 다시 만들어지면 캐시에는 여러 페이지가 남아 있어도 상태만 초기화됐습니다.
- **해결**: 펼침 여부를 상태로 두지 않고 캐시된 페이지 수에서 계산합니다(`data.pages.length > 1 || isFetchingNextPage || isFetchNextPageError`). 파생 가능한 상태를 따로 두지 않는다는 원칙이 `AGENTS.md`에 들어간 계기입니다.
- **검증**: 캐시에 2페이지가 있는 채로 다시 열었을 때 버튼 없이 센티널이 활성화되고 다음 커서를 요청하는지, 첫 "더보기" 실패 시 "다시 시도"만 보이는지 컴포넌트 테스트 2개를 추가했습니다.

## 4. 외부 리뷰·CodeRabbit 지적을 코드로 검증하기

- **방식**: 외부 리뷰나 다른 AI의 답변을 그대로 받지 않고, 에이전트에게 각 주장을 코드와 대조하게 했습니다. 유효한 것은 고치고, 사소한 것은 이유를 남기고 넘어갔습니다.
- **부하 테스트 스크립트 리뷰(CodeRabbit)**: 페이지 순회가 끝까지 갔는지 확인하지 않는 문제(`walkPages`가 `complete`를 반환하도록 수정, 댓글 시나리오에 '끝까지 순회' 체크 추가), Docker 실행 시 `host.docker.internal` 해석 옵션 누락, VUS 표의 실제 값과 설명 불일치를 모두 반영했습니다.
- **문서와 코드의 불일치 점검**: 에이전트가 README·결정 문서의 주장을 코드와 대조해, 쓰지 않은 E2E 도구를 사용한다고 적은 부분 등을 찾아냈고 문서에서 제거했습니다. 실행하지 않은 것을 실행한 것처럼 쓰지 않는다는 규칙이 여기서 나왔습니다.

## 5. 부하 테스트(k6)로 설계 결정 확인

- **목적**: 동시성 규칙(좋아요 카운트 정합성)이 부하에서도 지켜지는지, 어디가 먼저 병목이 되는지 수치로 확인합니다(`loadtest/`).
- **역할**: 시나리오 설계와 스크립트 초안은 에이전트와 함께 만들었고, 임계값은 요구사항이 아니라 초기 가정이라고 문서에 명시했습니다. 측정 실행과 결과 해석은 제가 했습니다.

## 에이전트와 일하면서 정한 규칙

| 겪은 문제 | 규칙 |
| --- | --- |
| 에이전트가 "아마 막혀 있을 것"이라고 답할 수 있음 | 코드를 읽어 사실부터 확인하고 답하게 한다 |
| 경합 테스트가 타이밍에 의존하면 불안정 | 락 대기 상태를 직접 만들어 결정적으로 검증한다 |
| 에이전트·AI 리뷰가 틀리거나 과한 지적을 섞음 | 코드로 검증한 뒤 반영하고, 반영하지 않을 때는 이유를 남긴다 |
| 에이전트 환경에서 실행하지 못한 검증 | 실행했다고 쓰지 않고 사람이 돌릴 명령을 안내한다 |
| 문서가 코드보다 앞서가거나 어긋남 | 문서의 주장을 코드와 대조한다 |
