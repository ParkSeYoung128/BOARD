# README 작성용 결정 기록 — 설계 결정과 트레이드오프

프로젝트 요구사항: 고정된 항목(Java/Spring Boot, Next.js/TypeScript, PostgreSQL, `docker compose up`) 외에는 모두 자유이며,
**선택 자체보다 선택한 이유**가 중요하다. README의 "설계 결정과 트레이드오프" 절은 아래 내용을 바탕으로 쓴다.

작성 원칙
- 항목마다 `결정 / 검토한 대안 / 이유 / 트레이드오프(포기한 것) / 코드 위치`를 적는다.
- "좋아서"가 아니라 이 프로젝트의 조건(데이터 규모, 요구사항, 삭제 정책, 동시성, 검증 방식)에서 출발한 이유를 쓴다.
- 코드 위치(파일·함수)는 구현이 끝난 뒤 실제 경로로 채운다. (CodeRabbit README 리뷰 기준과도 맞춘다.)
- 자율 결정 사항(요구사항에 없는 것)은 그렇다고 명시한다.

## A. 백엔드

### A1. 전체 구조: 모듈러 모놀리스 (MSA 미채택)
- 결정: 하나의 Spring Boot 앱 안에서 `post` / `comment` / `like` 패키지로 나눈다.
- 대안: 게시글·댓글 서비스 분리(MSA).
- 이유
  - 데이터 규모가 작다(게시글 39, 댓글 1,926, 가장 큰 글이 1,411). 독립 확장이 필요한 규모가 아니다.
  - 목록의 `commentCount`, "글이 삭제되면 댓글도 안 보임" 같은 규칙이 서비스 경계를 넘으면 목록 한 번에 서비스 간 호출이 붙거나, 카운트를 복제해 정합성 문제(이벤트 유실·중복)를 만든다. 지금은 한 DB의 서브쿼리와 한 트랜잭션으로 해결된다.
  - 요구사항이 단일 백엔드(`localhost:8080/api`, 9개 엔드포인트)와 `docker compose up` 한 번을 전제한다. MSA는 게이트웨이·서비스 간 인증·타임아웃·재시도·서비스별 DB가 늘어 기동·헬스체크·CI가 복잡해진다.
  - 검증할 정합성·경계 조건(동시 좋아요, 삭제 비노출, 페이지네이션 무중복)은 한 프로세스·한 DB일 때 통합 테스트로 증명하기 쉽다.
- 트레이드오프: 서비스별 독립 배포·확장·장애 격리를 포기한다. 대신 패키지 경계를 지키고(엔티티 간 JPA 연관관계 미사용, 조회 전용 쿼리) 나중에 `comment`를 떼어내기 쉽게 둔다.
- 트래픽 대비(이미 반영): 오프셋 없는 keyset, 부분 인덱스, 원자적 좋아요 갱신, 쿼리 수 테스트, 무상태 서버.
- 확장 시 고려(README에 명시): 인기 글 조회는 캐시·읽기 복제, 좋아요의 단일 행 락 경합은 카운터 분리나 비동기 집계, 분리가 필요해지면 `comment`부터 분리하고 그때 필요한 정합성 대책(비정규화 카운트 + 이벤트 등)을 함께 설계.
- 참고: 실제 병목은 서비스 경계가 아니라 인기 글의 좋아요 행 락 경합, 큰 글의 조회 쿼리다.

### A2. 데이터 접근: JPA + JPQL DTO 프로젝션 하이브리드
- 결정: 쓰기(글·댓글)는 JPA 엔티티, 읽기 목록은 JPQL 생성자 표현식 DTO 프로젝션, 좋아요와 시드는 JdbcTemplate.
- 대안: 순수 JPA(엔티티 조회 후 변환), JdbcClient/MyBatis 전면 사용.
- 이유
  - 목록은 `commentCount`, `isLiked`가 필요하다. 엔티티 조회 + 지연 로딩은 N+1이 되고, 컬렉션 fetch join + 페이징은 메모리 페이징이 된다. 그래서 연관관계 없이 서브쿼리를 포함한 프로젝션 한 번으로 가져온다(쿼리 수 테스트로 증명).
  - 삭제 정책은 `@SQLRestriction("deleted_at is null")`로 엔티티 경로 전반에 일괄 적용해 누락 위험을 줄인다.
  - 좋아요 카운트를 엔티티로 읽고 +1 하면 동시 요청에서 갱신이 유실된다. 그래서 원자적 SQL을 직접 쓴다. 시드는 대량 삽입·id 유지·`ON CONFLICT`가 필요해 JDBC 배치가 자연스럽다.
- 트레이드오프
  - JPA의 함정(N+1, 메모리 페이징, read-modify-write)을 스스로 피해야 한다. 그 책임을 테스트와 코드 리뷰 기준(CodeRabbit 지침)으로 관리한다.
  - `@SQLRestriction`은 JDBC/네이티브 쿼리에는 적용되지 않으므로 그 경로에는 `deleted_at is null`을 직접 명시해야 한다.
  - 두 가지 접근 방식이 섞여 일관성이 다소 떨어진다. 대신 "무엇에 무엇을 쓰는가"를 규칙으로 둔다(쓰기 엔티티 / 읽기 프로젝션 / 원자 갱신·대량 적재 JDBC).

### A3. 스키마
- 결정: `posts`, `comments`, `post_likes`(PK = post_id + user_id). id는 `GENERATED BY DEFAULT AS IDENTITY`, `like_count` 비정규화 컬럼(`CHECK >= 0`), 삭제는 `deleted_at`, 시각은 `TIMESTAMPTZ`(초 단위 절삭).
- 이유
  - `BY DEFAULT`: 시드의 id를 그대로 넣어야 한다. 적재 후 시퀀스를 `max(id)`로 맞춰 새 글 id 충돌을 막는다.
  - `post_likes`의 복합 PK가 사용자당 한 번만 누를 수 있다는 규칙을 DB가 보장한다. 동시 요청에서도 중복 삽입이 불가능하다.
  - `like_count` 비정규화: 목록 조회마다 `count(*)` 하지 않아도 된다. 대신 갱신은 원자적 `UPDATE`로만 하고 `CHECK`로 음수를 막는다.
  - `deleted_at`(boolean 아님): 삭제 시각을 남길 수 있고 `WHERE deleted_at IS NULL` 부분 인덱스와 궁합이 좋다.
  - 초 단위 절삭: 응답 형식(초 단위 ISO)과 DB 값이 같아 커서가 왕복해도 어긋나지 않는다.
- 트레이드오프: `like_count`가 인기 글의 단일 행 락 경합 지점이다(A1 확장 시 고려 참조). `post_likes`를 함께 유지해야 한다.

### A4. 마이그레이션: Flyway + `ddl-auto=validate`
- 이유: 부분 인덱스(`WHERE deleted_at IS NULL`)와 정렬 인덱스는 JPA 애노테이션으로 선언할 수 없어서 SQL 마이그레이션이 필요하다. 스키마의 진실을 Flyway 한 곳에 두고 Hibernate는 검증만 한다(엔티티와 스키마 불일치를 기동 시점에 발견).
- 트레이드오프: 스키마 변경 시 마이그레이션 파일을 새로 만들어야 하는 번거로움.

### A5. 페이지네이션: keyset (`created_at DESC, id DESC`)
- 결정: `limit + 1`개를 조회해 다음 페이지 여부를 판단하고, 불투명 커서 `base64url("{epochSecond}_{id}")`를 준다. 마지막 페이지는 `nextCursor: null`. `total`은 삭제 제외 전체 개수(count 쿼리 1회).
- 대안: offset/limit.
- 이유
  - 시드의 id 순서와 시간 순서가 일치하지 않아 id 단독 정렬은 틀리다. 같은 초에 만든 데이터가 많아 `(created_at, id)`를 함께 써야 동률에서도 무중복·무누락이다.
  - offset은 앞 페이지에 글이 추가·삭제되면 중복·누락이 생기고, 1,411개 같은 큰 목록에서 뒤로 갈수록 느려진다.
  - 부분 인덱스 `(created_at DESC, id DESC) WHERE deleted_at IS NULL`이 정렬과 삭제 필터를 함께 처리한다.
- 트레이드오프: 임의 페이지로 점프할 수 없다(무한 스크롤에는 문제 없음). 커서는 불투명 값이라 클라이언트가 해석하지 않는다.
- 자율 결정: `limit` 기본 20, 최대 50(초과는 50으로 보정, 1 미만은 400).
- 검증: 같은 초 동률, 1,411개 전체 순회, 순회 중 삭제 반영 테스트.

### A6. 좋아요 토글 동시성
- 결정: 한 트랜잭션에서 (글, 사용자) 단위 advisory lock(`pg_advisory_xact_lock`)을 먼저 잡고, `INSERT ... ON CONFLICT DO NOTHING` → 삽입되면 `like_count + 1`, 아니면 `DELETE` 후 `-1`. 카운트 갱신은 `UPDATE ... RETURNING`(0 미만 방지 `greatest`). 재시도 루프(최대 3회)는 사실상 도달하지 않는 안전장치로만 남긴다.
- 대안: 엔티티 read-modify-write, `@Version` 낙관적 락, `SELECT FOR UPDATE`, 유일 제약 + 재시도만으로 처리.
- 이유
  - 카운터는 DB가 원자적으로 증가시켜 lost update를 막는다.
  - 유일 제약만으로는 같은 사용자의 동시 연타에서 "삽입 → 삭제" 두 단계 사이에 요청이 끼어들 수 있고, 재시도 횟수를 넘기면 클릭이 반영되지 않는 결함이 있었다(CI에서 간헐적으로 실패로 확인). 같은 (글, 사용자) 요청을 advisory lock으로 한 줄로 세워 모든 클릭이 정확히 한 번씩 반영되게 했다. 다른 사용자끼리는 서로 기다리지 않는다.
  - `like_count` 컬럼은 `updatable = false`로 두어, 글 수정·삭제가 읽어 둔 옛 값으로 카운트를 덮어쓰지 못하게 한다(Hibernate는 기본으로 모든 컬럼을 UPDATE한다).
- 트레이드오프: JPA 밖의 SQL을 직접 관리한다. 같은 사용자가 연타하면 요청이 lock을 기다리는 동안 DB 커넥션을 하나씩 점유한다(Hikari 기본 풀 10). 인기 글에서는 `like_count` 행 락 경합이 남는다(부하 테스트로 수치 확인 예정).
- 검증: 다른 사용자 40명 동시 요청, 같은 사용자 홀수·짝수 연타, 여러 사용자 동시 연타 시 카운트 = 기록 수, 음수 방지, 글 수정·삭제가 좋아요 수를 덮어쓰지 않는지(결정적 재현 테스트).

### A7. 시드 적재
- 결정: JDBC 배치 + `ON CONFLICT (id) DO NOTHING`, 한 트랜잭션 + advisory lock, 삭제 id는 `deleted_at`을 채워 삽입, 적재 후 `setval`. `SmartInitializingSingleton`으로 웹 서버가 요청을 받기 전에 실행. 설정 플래그 `app.seed-enabled`.
- 대안: JPA `saveAll`, `ApplicationRunner`, 앱 밖 SQL 스크립트.
- 이유
  - 재기동해도 중복 적재·삭제 부활이 없어야 한다(멱등). id를 그대로 유지해야 한다.
  - `ApplicationRunner`는 서버가 뜬 뒤 실행되어 `/health` 200이어도 아직 적재 전일 수 있다. 서버 시작 전에 적재하면 `/health` 200이 곧 데이터 준비 완료다.
  - 동시 기동(여러 인스턴스)에도 advisory lock으로 안전하다.
- 트레이드오프: 시드가 커지면 기동이 느려진다(현재 규모에서는 무시할 수준). 시드 수정본은 기존 행을 덮어쓰지 않는다(의도된 멱등 동작).

### A8. 삭제 정책과 오류 규칙
- 결정: 게시글·댓글은 soft delete. 삭제된 리소스는 어디서나 404(존재 여부를 노출하지 않음). 글이 삭제되면 그 글의 댓글은 조회·작성·삭제 모두 불가. 판정 순서 404 → 403 → 400. 오류 본문 `{code, message}`.
- 이유: 요구사항의 삭제 정책을 모든 경로(목록, 상세, commentCount, 댓글, 좋아요)에서 일관되게 지키기 위해서다. 순서를 고정하면 클라이언트와 테스트가 예측 가능하다.
- 삭제와 댓글 작성·좋아요의 경합
  - 문제: 글 삭제는 soft delete(`deleted_at` UPDATE)라 FK가 막아 주지 않는다. 댓글 작성이 "글이 살아 있는지 확인(일반 SELECT) → INSERT"로 되어 있으면, 그 사이에 삭제가 커밋될 때 삭제된 글에 댓글이 생기고 201이 반환된다. 재현 테스트를 먼저 만들어 이 순서가 어긋남을 확인하고 고쳤다.
  - 결정: 댓글 작성은 글 행을 `FOR KEY SHARE`로 조회해 락을 쥔 채 INSERT하고, 글 삭제는 `FOR UPDATE`로 조회한 뒤 삭제한다. 둘이 충돌하므로 한쪽이 끝난 뒤 다른 쪽이 진행되고, 삭제가 먼저면 댓글 작성은 조건을 다시 평가해 404가 된다.
  - 락 모드 선택: `FOR SHARE`는 좋아요의 `like_count` UPDATE(NO KEY UPDATE)와 충돌해 인기 글에서 대기가 생긴다. `FOR KEY SHARE`는 이 UPDATE와 충돌하지 않아 좋아요 경합에 영향을 주지 않는다. 삭제 쪽에서 락 없이 UPDATE만 하면 KEY SHARE와 충돌하지 않으므로, 삭제도 반드시 `FOR UPDATE`여야 한다.
  - 좋아요는 별도 락이 없어도 안전하다. `UPDATE posts SET like_count = ... WHERE id = ? AND deleted_at IS NULL`이 삭제 트랜잭션의 행 락을 기다린 뒤 조건을 다시 평가해 0건이 되고, 404로 롤백되어 기록이 남지 않는다. 처음부터 이 경합을 의도한 설계라기보다 이 UPDATE 구조가 가진 성질이며, 같은 방식의 테스트로 확인했다.
  - 검증: `PostDeleteRaceTest`. 삭제 트랜잭션이 락을 쥔 채 커밋 전인 상태를 직접 만들고(타이밍에 기대지 않음), 요청이 락 대기 상태에 들어간 것을 `pg_stat_activity` 폴링으로 확인한 뒤 커밋해서 결과(404, 기록 없음)를 확인한다. 삭제·댓글·좋아요를 동시에 보내 교착 없이 끝나고 성공 응답을 받은 것만 저장되는지도 확인한다.

### A9. 검증 규칙
- 결정: 제목 20자는 **코드포인트** 기준(이모지 1자), 공백만인 값 거부, 입력값은 다듬거나 바꾸지 않고 그대로 저장. 내용 20,000자, 댓글 5,000자(자율 결정 상한).
- 이유: UTF-16 길이로 세면 이모지가 2자로 세어져 사용자가 보는 글자 수와 어긋난다. 입력값을 조용히 바꾸면 사용자가 입력한 것과 저장된 것이 달라진다.

### A10. 요청자 식별
- 결정: `x-user-id` 헤더 → 쿠키(URL 디코딩) → `demo_user`. `HandlerMethodArgumentResolver`로 `Requester`에 주입, 50자 초과 시 400.
- 이유: 로그인이 없는 요구사항라 컨트롤러가 헤더/쿠키를 직접 다루지 않게 한 곳에 모은다. 쿠키는 dev-user 화면이 URL 인코딩해서 저장하므로 디코딩이 필요하다.

### A11. 응답 필드
- 결정: 게시글·댓글 항목은 요구사항 예시의 필드만 사용한다. 목록 봉투에만 `nextCursor`를 추가한다(요구사항이 응답 설계를 자유로 둔 부분). `isLiked` 키는 `@JsonProperty("isLiked")`로 명시(Jackson이 `liked`로 바꾸지 않게).

## B. 프론트엔드

실무에서 흔한 선택(TanStack Query·Zustand·Tailwind·Radix)이 많지만, 이유는 모두 **이 프로젝트의 조건**에서 출발한다. 반대로 라이브러리를 쓰지 않은 선택(폼, 날짜, 무한 스크롤 감지)도 이유를 함께 적는다.

### B1. Next.js 15 App Router + 클라이언트 컴포넌트에서 데이터 호출
- 결정: 목록·상세·댓글 조회와 변경은 모두 브라우저(클라이언트 컴포넌트)에서 `fetch(..., { credentials: "include" })`로 호출한다. API 주소는 `NEXT_PUBLIC_API_BASE_URL`.
- 검토한 대안: 서버 컴포넌트에서 `cookies()`로 `x-user-id`를 읽어 헤더로 넘겨 호출(스타터가 서버용 `API_BASE_URL`을 함께 제공한다), 목록 첫 페이지만 서버에서 미리 불러오기.
- 이유
  - 모든 화면이 무한 스크롤·낙관적 업데이트처럼 **클라이언트 캐시가 중심**이다. 서버에서 미리 불러오면 TanStack Query의 `HydrationBoundary`로 서버 결과를 클라이언트 캐시에 이어야 하고, 목록(`['posts']`)과 상세(`['post', id]`) 두 캐시를 따로 맞춰야 해서 복잡도가 늘어난다.
  - 로그인 뒤에 보는 모바일 커뮤니티 화면이라 SEO 요구가 없다.
  - 참고로 쿠키는 포트를 구분하지 않아 `localhost:3000`에서 dev-user 화면이 설정한 `x-user-id` 쿠키가 `localhost:8080`에도 전송된다. 그래서 브라우저 호출에 `credentials: "include"`만 붙이면 요청자가 전달된다.
- 포기한 것: 첫 화면이 로딩 상태로 시작하고 요청이 순차로 이어질 수 있다(서버 첫 페이지 미리 불러오기는 검토 후 보류). SSR 이점도 쓰지 않는다.
- 코드 위치: `frontend/shared/api/client.ts`

### B2. 서버 상태: TanStack Query
- 결정: 서버에서 받아온 데이터의 유일한 출처를 쿼리 캐시로 둔다. 키: `['posts']`(무한), `['post', id]`, `['comments', id]`(무한).
- 검토한 대안: SWR(`useSWRInfinite`는 쓸 수 있지만 낙관적 업데이트의 롤백과 여러 캐시 동기화를 직접 처리할 부분이 더 많다), Redux Toolkit Query, `useEffect` + `useState` 직접 구현.
- 이유
  - 이 프로젝트의 핵심은 **같은 게시글 데이터가 여러 캐시에 흩어져 있다**는 점이다. 좋아요 수와 댓글 수는 목록(`['posts','list']`의 여러 페이지)과 상세(`['posts','detail', id]`)에 동시에 있다. 쿼리 키는 `postKeys` 팩토리 한 곳에 모아 두었다. 한 번 바꾸면 두 곳을 함께 맞춰야 하고, 실패하면 둘 다 되돌려야 한다. 이 동기화(낙관적 반영, 롤백, 무효화)를 라이브러리에 맡긴다.
  - 목록·댓글은 `nextCursor === null`이면 끝나는 커서 기반 무한 스크롤이라 `useInfiniteQuery`가 그대로 맞는다.
- 구현 규칙
  - 좋아요 토글: 누르는 즉시 하트와 숫자를 바꾸고(낙관적 반영), 서버가 `{isLiked, likeCount}`를 돌려주면 무효화(다시 조회)하지 않고 **응답값으로 두 캐시를 덮어쓴다**. 클라이언트가 +1·−1을 이어 계산하지 않고 서버 값을 기준으로 삼아, 다른 사용자의 좋아요가 섞여도 어긋나지 않는다. 같은 글의 요청은 mutation `scope`로 한 번에 하나씩 순서대로 보내고(서버는 같은 사용자의 연타를 advisory lock으로 한 줄로 처리한다, A6), 연타 중에는 **마지막 응답만** 화면에 반영해 앞선 응답이 도착할 때마다 하트가 깜빡이는 것을 막는다. 시작 전에는 `cancelQueries`로 진행 중인 조회를 취소해 오래된 응답이 낙관적 값을 덮지 못하게 한다. 실패하면 시작 전 스냅샷으로 되돌리지 않는다(연타 중에는 앞서 성공한 요청까지 취소하게 된다). 대신 글마다 **마지막으로 서버가 확정한 값**을 기억해 두었다가, 실패한 요청을 뺀 나머지 대기 중 토글을 그 위에 다시 적용해 화면을 되돌리고 토스트를 띄운다. 대기 중인 요청이 없으면 서버 상태를 다시 조회해 맞추는데, 이 재조회까지 실패해도 화면이 낙관적 값에 머물지 않는다.
  - 댓글 목록: 처음에는 `limit=2`, "더보기" 이후에는 `cursor`+`limit=20`(요구사항)이며 더보기는 `total > 2`일 때만 보인다. 페이지 크기를 **커서 유무로 정하는 요청 함수**(`pageParam ? 20 : 2`)에 넣어, 댓글을 쓰거나 지운 뒤 모든 페이지를 다시 조회해도 첫 페이지는 계속 2개, 나머지는 20개 단위로 모양이 유지된다. 더보기를 누른 뒤에는 글 목록과 같은 센티널로 이어 불러오고, 오류는 첫 페이지(영역 오류)·다음 페이지(목록 유지 + 다시 시도)로 나눈다.
  - 댓글 작성·삭제와 댓글 수: 응답에 글의 댓글 수가 없어 성공 시 글 캐시(상세·목록)의 `commentCount`를 ±1 하고 댓글 목록은 다시 조회한다. 삭제 후 다시 조회하지 않으면 첫 페이지(2개)에서 하나가 빠졌을 때 뒤에 댓글이 남아 있는데도 "더보기"가 사라진다(`total > 2` 조건 때문). 삭제의 404(이미 삭제됨)는 성공으로 보고, 작성·삭제 모두 재조회가 끝날 때까지 mutation 을 대기 상태로 두어 입력창·확인 팝업이 중복 제출되지 않게 한다. 댓글 키는 글 키(`['posts',…]`) 밖(`['comments', postId]`)에 둬서 좋아요의 취소·무효화가 댓글 페이지를 흔들지 않게 했다.
  - 댓글 입력창: 한글 조합 중 Enter 는 제출하지 않는다(일부 브라우저가 조합 확정 Enter 로 폼을 제출한다). 5,000자 제한은 서버와 같은 코드포인트 기준이며 초과하면 전송 아이콘이 사라진다(방어용 값, 자율 구현).
  - 작성·수정 폼(공통): 제목 20자는 서버와 같은 **코드포인트** 기준이고 `maxLength` 속성은 쓰지 않는다(UTF-16 단위로 세고 일부 브라우저에서 한글 조합을 깨뜨린다). 한글 조합 중에는 자르지 않고 조합이 끝날 때 입력창의 실제 값(`currentTarget.value`)으로 자른다 — 브라우저마다 `input`/`compositionend` 순서가 달라 state 를 믿을 수 없기 때문이다. 모바일에서는 조합 중에 "작성 완료"를 누를 수 있어 **제출 시점에 한 번 더 검증하고 자른 값을 보낸다**. 내용 20,000자(방어용, 자율 구현)는 자르지 않고 안내 문구와 함께 제출만 막는다. 판단에만 `trim()`을 쓰고 전송은 원문이다. 제목에서 Enter 는 제출 대신 내용 칸으로 이동한다.
  - 수정 화면의 초기값: `usePost` 는 목록 캐시를 placeholder 로 먼저 보여 주므로, 폼 초기값을 `data` 에 그대로 연결하면 오래된 값이 보이고 뒤늦게 온 서버 값이 입력 중인 내용을 덮어쓴다. **서버 응답(placeholder 가 아닌 것)이 도착한 뒤에만 폼을 그리고**, 폼은 `key={post.id}` 로 한 번 만들어 초기값을 마운트 때만 넣는다. 이후 재조회가 일어나도 입력은 유지된다.
  - 작성·수정 후 이동: 작성은 `router.replace("/")`(뒤로가기로 등록된 글이 채워진 폼에 돌아와 중복 등록하는 것을 막는다)이고 성공 시 목록 캐시를 `resetQueries` 로 비워 다음에 목록이 열릴 때 처음부터 다시 받는다(최신순 맨 위에 새 글이 오는 것을 서버 기준으로 보장). 수정은 상세의 "수정하기"로 들어왔을 때만(`?from=detail`) `router.back()` 으로 돌아가 상세가 기록에 두 번(목록 → 상세 → 상세) 쌓이지 않게 하고, 그 밖에는 `router.replace` 로 상세에 간다. 처음에는 `history.length > 1` 로 "돌아갈 기록이 있는지" 를 판단했으나, 이 값은 세션 기록 전체의 길이라 직전 항목이 이 글의 상세라는 보장이 없다(외부 사이트에서 주소로 들어와도 2 이상이라 수정 후 외부 사이트로 이동한다). 그래서 이동 출처를 주소로 명시했다. 표시 값이 남은 주소를 공유·북마크해 들어오는 경우는 남는 한계지만, 표시 없이 추정하는 것보다 오동작 범위가 좁다.
  - 수정의 오류 처리: 본인 글이 아니면 폼 대신 상세로 돌려보내고(서버도 403 으로 거부), 제출 시 403(다른 탭에서 사용자를 바꾼 경우)이면 토스트 후 상세로 보낸다. 404(다른 곳에서 삭제)는 상세를 다시 조회해 "없는 글" 화면으로 넘긴다. 그 밖의 실패는 토스트만 띄우고 입력을 유지한다.
  - 문구(자율 구현): 작성 완료 토스트는 시안·`architecture.md` 문구 "게시글이 등록되었습니다."를 쓴다. 수정 화면은 요구사항이 "작성 화면과 동일"이라고만 해서 구조는 같게 두고 헤더·버튼 문구만 "글수정"/"수정 완료"로 바꾸었으며, 수정 성공 토스트("게시글이 수정되었습니다.")는 요구사항에 없는 추가다.
  - 댓글 작성·삭제: 상세의 `commentCount`와 목록 카드의 댓글 수를 함께 갱신한다.
- 포기한 것: 의존성이 하나 늘고, **쿼리 키를 잘못 설계하면 목록과 상세가 어긋날 위험을 직접 진다.** 그래서 키 구성을 한 파일에서만 정의한다.
- 코드 위치: `frontend/features/posts/queries.ts`, `frontend/features/comments/queries.ts`

### B3. UI 전역 상태: Zustand(토스트 한정) + 컴포넌트 로컬 상태
- 결정: 모달·시트 열림과 입력값은 컴포넌트 로컬 `useState`, 화면 이동을 넘는 상태인 **토스트만** Zustand 스토어에 둔다.
- 검토한 대안: 루트 `layout`에 둔 Context Provider(App Router의 루트 layout은 화면을 이동해도 다시 마운트되지 않으므로 이것으로도 토스트는 유지된다), `sonner` 같은 토스트 라이브러리, 쿼리 파라미터(`?toast=created`, 새로고침하면 토스트가 다시 뜨는 문제).
- 이유
  - 토스트는 mutation의 `onSuccess` 같은 **컴포넌트 밖에서 호출**된다. Zustand는 Provider 없이 `useToast.getState().show(...)`로 어디서든 호출할 수 있고, 구독하는 컴포넌트만 다시 렌더링된다. Context는 호출하는 쪽이 훅 안에 있어야 하고, 값이 바뀌면 소비하는 모든 컴포넌트가 다시 그려진다.
  - 쿼리 파라미터 방식은 새로고침이나 뒤로 가기에서 토스트가 다시 노출된다.
- 포기한 것: 상태 하나를 위해 의존성을 추가했다. Context로도 충분히 만들 수 있으나, 컴포넌트 밖 호출과 불필요한 재렌더링을 피하는 쪽을 택했다.
- 코드 위치: `frontend/shared/store/toast.ts`

### B4. 스타일링: Tailwind CSS v4(`@theme` 토큰)
- 결정: 피그마에서 측정한 색·간격·글자 크기를 `@theme`에 등록한다.
- 검토한 대안: CSS Modules, styled-components·emotion, MUI 같은 완성형 UI 라이브러리.
- 이유
  - `@theme`에 토큰을 등록하면 그 값이 유틸리티 클래스가 되어, **토큰 밖의 값을 쓰기 어렵다**(하드코딩 방지). 디자인 토큰이 곧 코드의 어휘가 된다.
  - 런타임이 없는 CSS라서 App Router·서버 컴포넌트와 충돌이 없다. styled-components·emotion은 App Router에서 클라이언트 전용 처리와 별도 레지스트리 설정이 필요하다.
  - 완성형 UI 라이브러리는 시안과 픽셀을 맞추기 어렵고 번들이 크다.
- 포기한 것: 클래스 문자열이 길어진다. 그래서 반복되는 UI(카드, 버튼, 헤더)는 컴포넌트로 뽑고, 컴포넌트 밖에서 같은 클래스 묶음을 복사하지 않는다는 규칙을 둔다.
- 확인 사항: Docker(alpine) 빌드를 위해 `package-lock.json`에 Tailwind v4 네이티브 musl 바이너리가 포함되는지 검증한다.
- 코드 위치: `frontend/app/globals.css`(`@theme`)

### B5. 바텀시트·확인 팝업: Radix UI Dialog
- 결정: 삭제 확인 팝업과 ⋯ 메뉴 바텀시트는 Radix Dialog를 바탕으로 직접 스타일링한다. shadcn CLI는 쓰지 않고 필요한 컴포넌트만 작성한다.
- 검토한 대안: `vaul`(Radix Dialog 기반 drawer), 직접 구현, 헤드풀 UI 라이브러리.
- 이유: 포커스 트랩·ESC·`aria`·스크롤 잠금 같은 접근성 처리는 직접 짜기 까다롭고 틀리기 쉽다. Radix는 **동작만 제공하고 모양이 없는(헤드리스)** 라이브러리라 피그마와 픽셀을 맞출 수 있다.
- 포기한 것: Dialog로 만든 바텀시트에는 **스와이프로 닫기가 없다.** `vaul`이 이 제스처를 제공하지만 시안에 제스처 요구가 없어 제외했다.
- 코드 위치: `frontend/shared/ui/BottomSheet.tsx`, `frontend/shared/ui/ConfirmDialog.tsx`

### B6. 폼 검증: 직접 구현(react-hook-form·zod 미사용)
- 결정: `canSubmit = 제목 코드포인트 1~20자(공백만 불가) && 내용 비어 있지 않음`을 순수 함수로 두고, 작성·수정 폼이 함께 쓴다.
- 검토한 대안: react-hook-form + zod.
- 이유
  - 필드가 2개뿐이고 비동기 검증이 없다.
  - 붙여넣기 절단과 `n/20` 글자 수 카운터 때문에 어차피 **제어 컴포넌트가 필요해서** react-hook-form의 비제어 방식이 주는 이점이 없다. (코드포인트 길이 검증 자체는 zod의 `refine` 한 줄로도 가능하므로 라이브러리와 맞지 않아서가 이유는 아니다.)
- 주의한 점
  - **한글 IME 조합 중에는 절단하지 않는다.** 조합 중에 값을 자르면 글자가 깨진다. `compositionend` 이후에 코드포인트 기준으로 절단한다.
  - 코드포인트 기준은 서버의 Java `codePointCount`와 JS `[...s]`가 일치한다. 다만 👨‍👩‍👧 같은 결합 이모지는 화면에서는 1자로 보이지만 여러 코드포인트로 센다. **서버와의 일치를 우선해 grapheme 기준은 포기했다.**
- 포기한 것: 폼이 커지면 재사용성이 떨어진다(이 프로젝트에서는 해당 없음).
- 코드 위치: `frontend/shared/lib/codepoint.ts`, `frontend/features/posts/PostForm.tsx`

### B7. 무한 스크롤 감지: IntersectionObserver 직접 사용
- 결정: 목록 끝에 센티널 요소를 두고 `IntersectionObserver`로 화면 진입을 감지해 `fetchNextPage`를 호출한다. 댓글은 "더보기" 이후에만 같은 센티널을 켠다.
- 검토한 대안: `react-intersection-observer`, 스크롤 이벤트 계산.
- 이유: 필요한 기능이 센티널 하나의 진입 감지뿐이라 훅 하나(약 20줄)로 충분하다. 스크롤 이벤트 계산은 레이아웃 계산 비용이 크다.
- 포기한 것: 라이브러리가 처리하는 엣지 케이스(`rootMargin`, 언마운트 정리)를 직접 챙긴다.
- 코드 위치: `frontend/shared/ui/InfiniteSentinel.tsx`

### B8. 시간 표기: 순수 함수 + `Intl`(날짜 라이브러리 미사용) + 경계값 테스트
- 결정: 목록은 항상 상대 시간, 상세 본문은 `yy.MM.dd`(시안), 댓글은 **30일 미만만 상대**(자율 결정), 날짜 포맷은 `Asia/Seoul` 고정, 숫자는 천 단위 쉼표(`toLocaleString('ko-KR')`).
- 검토한 대안: date-fns, dayjs.
- 이유: 필요한 것이 상대 시간과 `yy.MM.dd` 두 가지뿐이고 시간대도 하나로 고정이라 `Intl.DateTimeFormat`과 작은 함수로 충분하다. 실수하기 쉬운 경계(59초/60초, 23시간/24시간, 6일/7일, 29일/30일, 364일/365일)는 순수 함수로 분리해 테스트한다. 30일 기준은 요구사항에 없는 자율 결정임을 README에 명시한다.
- 포기한 것: 다국어·복잡한 포맷으로 확장할 때 직접 고쳐야 한다.
- 코드 위치: `frontend/shared/lib/time.ts`

### B9. 테스트 도구: Vitest + React Testing Library
- 결정: 순수 함수·컴포넌트·화면 흐름(API는 가짜 서버로 대체)을 Vitest + React Testing Library로 검증한다. 브라우저 E2E는 작성하지 않았다.
- 검토한 대안: Jest(Next.js의 SWC·ESM 설정이 추가로 필요), Playwright·Cypress(E2E).
- 이유: Vitest는 TypeScript·ESM 설정이 단순하고 빠르다. 요청자 전환(본인 글·남의 글)은 쿠키 값을 바꿔 컴포넌트 테스트에서 검증한다.
- 포기한 것: 실제 브라우저·서버를 함께 띄우는 E2E. Docker·DB가 필요해 CI에 넣기 무겁고, 화면 흐름은 컴포넌트 테스트로 대신했다.

### B10. 디자인 구현 방침
- 시안(PNG)과 요구사항이 다르면: 시안에만 있는 요소는 시안에 맞추되, 요구사항에 없는 요소(오버레이 프레임에만 보이는 조회수·"첫 댓글로 이동"·댓글 좋아요/답글쓰기/수정·"수정됨" 등)는 제외하고 "남은 과제"에 기록한다.
- 글자 크기는 글리프 높이로 추정한 값이므로 구현 후 시안과 겹쳐 보며 보정한다.
- 댓글 흐름: 최초 2개 → 더보기(`total > 2`일 때만) → 무한 스크롤. 아바타는 작성자명 해시로 3종 중 고정 선택.

## C. 테스트 전략
- 백엔드: **실제 PostgreSQL 16(Testcontainers)** 위에서 통합 테스트. H2를 쓰지 않은 이유는 부분 인덱스, `ON CONFLICT`, `RETURNING`, advisory lock 등 이 프로젝트의 핵심 동작이 PostgreSQL 전용이기 때문이다. H2로는 실제 동작을 증명할 수 없다.
- 검증 항목: keyset 순회(무중복·순서, 같은 초 동률, 댓글 1,411개), 삭제 데이터 비노출, 권한(404→403→400), 좋아요 동시성, 쿼리 수(N+1), 시드 재적재 멱등, 검증 규칙(이모지), 요청자 식별.
- 프론트엔드: Vitest + React Testing Library(시간 유틸, 폼 검증, 컴포넌트 동작, 화면 흐름).
- 트레이드오프: Testcontainers는 Docker가 필요하고 느리다. 대신 프로덕션과 같은 DB로 검증한다.

## C2. 부하 테스트 결과 (k6, `loadtest/`)

- 목적: 현재 구조(단일 Spring Boot + PostgreSQL)가 어느 정도 부하에서 어떻게 동작하는지, 그리고 **동시성 규칙(좋아요 카운트 정합성)이 부하에서도 지켜지는지**를 수치로 확인한다. 요구사항의 요구가 아니라 설계 결정(A1, A5, A6)의 근거 자료다.
- 환경: Apple M5(10코어) / 메모리 24GB 노트북 한 대에서 k6와 서버·DB를 함께 실행했다. Docker Desktop 할당 자원은 CPU 10개, 메모리 약 7.75GiB. 서버 설정은 기본값(Hikari 풀 10, Tomcat 스레드 200 — `application` 설정과 compose 에 따로 지정하지 않았다). 시드 데이터는 글 39개·댓글 1,926개. **같은 머신에서 k6가 CPU를 나눠 쓰므로 절대 성능이 아니라 "이 환경에서의 값"이다.**
- 측정 방식: 읽기 3종(`feed`·`comments`·`mixed`)은 1회, `likes`와 `likes_multi`는 3회 실행해 중앙값과 범위를 적었다(1회차는 워밍업 영향이 섞여 있다). 요약표의 p95는 `http_req_duration`의 `name` 태그별 값이다.

### 정합성 (가장 중요한 결과)

- 3회 모두 모든 검증이 맞았다. burst·sustained 는 요청마다 새 사용자 id 를 써서 **좋아요를 켜는 경로만** 부하를 받았고, 켰다 끄는(취소, `like_count - 1`) 경로는 한 사용자의 연타(spam)와 아래 여러 사용자 연타(`likes_multi`)가 받았다.
  - burst: 최종 `likeCount` = 500 (3회 모두)
  - sustained: 최종 `likeCount` = 적용 수 (51,362 / 76,266 / 54,829)
  - spam: 최종 `likeCount` = 적용 수를 2로 나눈 나머지 (적용 72,158 → 0, 75,127 → 1, 73,934 → 0)
  - **여러 사용자 연타(`likes_multi`)**: 100명이 각자 같은 글에 켜기·끄기를 번갈아 약 200번씩(회차당 20,050건 = 켜기 10,050 + 끄기 10,000) 눌렀고, 3회 모두 최종 `likeCount` = 50 = 기대값(성공한 토글 수가 홀수인 사용자 수)이었다. 요청은 모두 성공했고 `likeCount`가 음수가 된 응답도 없었다(checks 100%).
- 의미: 같은 사용자의 연타를 advisory lock 으로 한 줄로 세우고 카운터를 원자적 UPDATE 로 갱신하는 설계(A6)가, 서로 다른 사용자의 켜기·끄기가 같은 글 행에서 뒤섞이는 가장 거친 경우까지 포함해 부하에서도 지켜졌다. 이 설계의 근거를 통합 테스트(40명 동시, 홀수·짝수 연타)에 더해 실제 서버·DB 위의 대량 요청으로도 보였다.

### 해석 (사실과 가설을 구분)

- 사실: 이 환경과 부하에서 읽기·댓글·혼합 모두 p95가 한 자릿수 ms이고 오류가 없다. 댓글은 깊은 페이지에서도 지연이 일정하다(keyset, `idx_comments_by_post`).
- 사실: 100명이 각자 연타해도(`likes_multi`) p95 57ms로 회차 간 차이가 작고(56~59ms), 사용자별 소요 시간도 6.9~7.4초로 거의 같아 특정 사용자가 밀리지 않았다. sustained(68~98ms, 회차마다 크게 흔들림)보다 오히려 안정적이다.
- 사실: 좋아요는 읽기보다 확실히 느리다. 같은 글 한 행에 갱신이 몰리고, `likes.js`는 요청 사이 대기가 없어 처리량이 곧 해당 동시성에서의 용량에 가깝다(약 1,700~2,500 req/s).
- 가설(미검증): 같은 글 한 행에 대한 갱신 처리량은 약 3,700 req/s 근처가 상한일 수 있다(한 사용자의 spam 이 행과 lock 을 직렬로 쓰며 낸 값). `likes_multi`(약 2,700)는 그 약 73%, sustained(약 1,700~2,500)는 그 아래다. 상한이 같은 행의 직렬 처리 때문인지, DB 왕복·k6 의 CPU 때문인지는 구분하지 못했다.
- 가설(미검증): burst·sustained의 수십 ms 지연은 동시 사용자(100~200)가 Hikari 풀(10)보다 많아 생기는 **커넥션 대기**이거나, 같은 글의 `like_count` 행 락 대기일 것이다. 둘은 이 데이터만으로 구분되지 않는다. 풀 크기를 바꿔 `sustained`만 다시 돌려 보면 가릴 수 있다(풀이 원인이면 풀을 키울수록 지연이 줄고, 행 락이면 거의 줄지 않는다). **미실시.**
- spam이 가장 빠른 것은 같은 사용자의 요청이 advisory lock 으로 줄 서지만 동시 연결이 10개라 풀 대기가 없기 때문으로 본다. 반대로 같은 사용자가 연타하는 동안 그 요청들이 lock 을 기다리며 커넥션을 점유하는 트레이드오프(A6)는 다른 트래픽이 섞인 상황에서는 측정하지 않았다.

### 한계와 주의

- 읽기 시나리오(`feed`·`comments`·`mixed`)는 요청 사이 대기가 있어 **서버의 한계를 찾은 것이 아니다.** "이 부하에서 느려지지 않는다"까지만 말할 수 있고, 몇 명까지 버티는지는 모른다(사용자 수를 크게 올린 추가 측정은 미실시).
- 회차 간 변동이 크다(`sustained` 적용 수 51,362~76,266, 평균 지연 39~58ms). 팬 없는 노트북과 같은 머신의 k6 영향으로 보며, 값은 범위와 함께 읽어야 한다.
- 스크립트의 임계값(읽기 300~500ms, 좋아요 500~1,500ms)은 초기 가정이라 실측보다 훨씬 느슨하다. 조정 여부는 미정.
- 여러 사용자 연타는 사용자당 연결 1개(화면에서의 연타와 같다)만 측정했다. 한 사용자가 연결 여러 개로 동시에 누르며 lock 대기로 커넥션을 점유하는 경우(A6 트레이드오프, `MULTI_CONN`)는 측정하지 않았다.
- 단일 인스턴스·단일 DB 기준이며, 인스턴스를 늘렸을 때의 동작(advisory lock 은 인스턴스 간에도 유효하나 풀·DB 부하는 다름)은 측정하지 않았다.

## D. 빌드·실행·협업
- 빌드 도구: 스타터 기본인 Gradle 유지(바꿀 이유가 없고 스타터와의 호환이 이득). 백엔드는 Java 17 toolchain.
- 실행: `docker compose up` 한 번으로 DB·백엔드·프론트 기동, 헬스체크(`/health` 200 유지), 포트는 환경 변수로 변경 가능.
- 테스트 실행(README "테스트" 절에 그대로 쓸 문구): Docker를 켠 상태에서 `cd backend && ./gradlew test` (Testcontainers가 PostgreSQL 16 컨테이너를 자동으로 띄웁니다. Docker Engine 29 이상에서 접속 오류가 나면 `echo "api.version=1.44" >> ~/.docker-java.properties`를 한 번 실행하세요.)
  - 배경: Docker Engine 29부터 최소 API 버전이 1.44로 올라갔는데, Spring Boot 3.5가 쓰는 Testcontainers 1.x는 더 낮은 버전으로 접속해 400 오류가 난다. 1.x에는 수정 릴리스가 없어 API 버전을 지정하는 우회 방법을 쓴다.
  - 미정: 저장소에 `backend/src/test/resources/docker-java.properties`(`api.version=1.44`)를 넣으면 개인 설정 없이 동작한다. 넣으면 위 문구에서 우회 안내를 뺀다.
- CI: GitHub Actions에서 PR마다 백엔드 `./gradlew test`(프론트는 구현 후 추가). checkout 자격 증명 저장 비활성화 등 최소 권한(`contents: read`).
- 협업 방식: 이슈/PR 템플릿, 브랜치별 PR, CodeRabbit 자동 리뷰(`.coderabbit.yaml`에 영역별 리뷰 기준 명시).
