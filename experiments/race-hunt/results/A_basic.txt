  위치(클래스.메서드): PostService.update ↔ LikeService.toggle
  동시 요청 조합: 작성자의 PATCH + 다른 사용자의 좋아요 토글 (같은 글)
  인터리빙 (T1/T2 단계별): ① T1 findLive로 Post를 읽음 (likeCount=100, 잠금
  없음)
  ② T2가 post_likes에 INSERT하고 like_count+1로 101 저장 후 커밋 ③ T1이 flush
  시 update posts set ...,  like_count=100, ... where id=? 실행 후 커밋. T2가
  T1 flush 전에 UPDATE까지 했다면 T1이 행 잠금을 기다렸다가, 커밋 후 같은
  조건으로 다시 평가해 100으로 덮어씀
  깨지는 불변식 / 결과: like_count와 post_likes 기록 수 일치 불변식이 깨짐.
  좋아요 기록은 있는데 카운트에 반영되지 않음(lost update). 반대로 취소가
  사라지면 카운트가 실제보다 커짐. decrement의 greatest(...,0) 때문에 어긋남이
  0에서 가려져 드러나지 않을 수 있음. 인기 글일수록 잘 일어남
  확신도: 상
  재현 테스트 아이디어: TransactionTemplate으로 T1을 열고
  posts.findByIdAndDeletedAtIsNull로 읽은 뒤 edit 호출. 커밋 전에 별도
  스레드에서 likeService.toggle을 실행하고 join해서 커밋까지 끝냄(T1은 아직
  잠금이 없어 막히지 않음). 이어서 T1 커밋. like_count == 초기값+1이고
  count(post_likes)==1인지 검증. sleep 없이 순서가 결정됨
  수정 후보: likeCount에 @Column(insertable=false, updatable=false)(DB 기본값 0
  사용) 지정 + @DynamicUpdate. 또는 findLive에 PESSIMISTIC_WRITE 대신 FOR NO 
  KEY UPDATE 사용(FOR UPDATE는 FK KEY SHARE와 충돌해 댓글·좋아요 INSERT까지
  막음)

  인터리빙 (T1/T2 단계별): ① T1 requireLivePost에서 existsLive가 true(스냅샷

  에이전트는 코드만 읽고 이렇게 판단했습니다. 코드를 실행하지 않았고, 저도 위

  - F1~F3의 공통 원인: 에이전트는 Post 엔티티에 @DynamicUpdate, @Version,
    updatable=false가 하나도 없다고 봤습니다. 그래서 Hibernate가 저장할 때마다
    like_count와 deleted_at을 포함한 모든 컬럼을 덮어쓴다는 것입니다.
  - 검토하지 못한 부분: 이 스냅샷에는 SeedLoader가 없어서 시드 적재 경로는
    검토하지 못했다고 합니다. docs/architecture.md에는 이 클래스가 있다고 적혀
    있습니다.
  - 안전하다고 본 부분: 같은 사용자의 좋아요 연타, 서로 다른 사용자의 동시
    좋아요, 데드락, 음수 like_count는 안전하다고 판단했습니다.
