## D1. 한 사용자의 좋아요 연타 경합 (수정: 32b3c31, PR #7 안)
- 위치: `LikeService.toggle` (`insertIfAbsent` → 실패 시 `delete` 2단계 + 재시도 3회)
- 메커니즘: 같은 사용자의 요청이 "삽입 시도"와 "삭제 시도" 사이에 끼어들면, 두 요청이 서로의 결과를 상쇄하거나 재시도 후에도 클릭이 반영되지 않는다. 유일 제약은 중복 삽입만 막을 뿐 요청 순서를 직렬화하지 않는다. 홀수 번 눌렀는데 최종 상태가 '좋아요 아님'이 될 수 있다.
- 실제 해결: (글, 사용자) 단위 `pg_advisory_xact_lock`으로 같은 사용자의 요청만 직렬화.
- 탐지 인정 기준(○): 같은 사용자의 동시 토글에서 최종 상태/클릭 유실 문제를 지적하고, 유일 제약이나 재시도로는 충분하지 않다는 점을 짚는다.

## D2. 글 수정·삭제 시 like_count 덮어쓰기 (수정: PR #11)
- 위치: `Post` 엔티티 `likeCount` 필드, `PostService.update` / `delete`
- 메커니즘: Hibernate 변경 감지는 기본적으로 모든 컬럼을 UPDATE한다. 수정/삭제 트랜잭션이 읽어 둔 옛 `like_count`로, 그 사이 원자적 UPDATE로 증가한 값을 덮어쓴다.
- 실제 해결: `@Column(updatable = false)`, 카운트는 원자적 SQL로만 변경.
- 탐지 인정 기준(○): 수정 또는 삭제가 엔티티 저장 시 like_count를 함께 써서 동시 좋아요 결과를 덮어쓴다는 점을 지적.

## D3. 글 삭제 중 댓글 작성 (수정: PR #23)
- 위치: `CommentService.create` (글 존재 확인 → INSERT)
- 메커니즘: 삭제가 소프트 삭제(UPDATE)라 FK가 막아 주지 않는다. "글 확인"과 "댓글 INSERT" 사이에 삭제가 커밋되면 삭제된 글에 댓글이 생기고 201이 반환된다.
- 실제 해결: 댓글 작성은 글 행을 `FOR KEY SHARE`, 삭제는 `FOR UPDATE`로 잡아 서로 기다리게 함.
- 탐지 인정 기준(○): 확인 후 실행 사이의 삭제 커밋으로 삭제된 글에 댓글이 달리는 시나리오를 지적.

## D4. 글 수정·삭제 경합으로 삭제된 글이 되살아남 (수정: PR #27)
- 위치: `PostService.update` (`findLive` → 필드 변경 → 변경 감지 UPDATE)
- 메커니즘: 수정 트랜잭션이 삭제 전 상태(deleted_at = null)를 읽은 뒤, 삭제가 먼저 커밋돼도 수정의 UPDATE가 모든 컬럼을 쓰면서 `deleted_at = null`로 덮어써 글이 되살아난다.
- 실제 해결: 수정도 먼저 글 행을 `FOR NO KEY UPDATE`로 잡고, 삭제가 먼저 커밋됐으면 404.
- 탐지 인정 기준(○): 수정이 deleted_at을 null로 덮어써 삭제를 무효화하는 시나리오를 지적.

## 참고: 안전한 경로 (보고하면 오탐 판정 후보)
- 글 삭제 중 좋아요: `UPDATE ... WHERE id = ? AND deleted_at IS NULL`이 삭제의 행 락을 기다린 뒤 조건을 재평가해 0건 → 404 → 롤백. 단, 이 시점 코드에서 해당 쿼리 형태가 실제로 그런지 확인 후 판정할 것.
