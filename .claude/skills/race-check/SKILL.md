# race-check — 동시성 경합 점검 절차

`experiments/race-hunt`의 결과를 절차로 만든 것이다. 에이전트는 경합을 잘 찾지만, 심각도 판정과 "안전하다"는 결론은 틀릴 수 있다. 그래서 탐지는 에이전트에게, 판정과 검증은 테스트와 사람에게 맡긴다.

## 1. 탐지: 체크리스트 에이전트 실행
`race-hunter-checklist` 서브에이전트에게 변경된 쓰기 경로(없으면 전체 백엔드)를 점검시킨다. 에이전트는 읽기 전용이며 표로만 보고한다.

## 2. 판정: 에이전트 결론을 그대로 믿지 않는다
- 각 항목마다 `AGENTS.md`의 불변식 중 무엇이 깨지는지 확인한다. 깨지는 불변식이 없으면 심각도를 낮춘다.
- **"안전하다"고 판정된 조합, 특히 같은 사용자·같은 키의 중복 요청(연타)은 코드로 다시 확인한다.** 일반 지시를 받은 에이전트가 이 경우를 "안전"이라고 단정한 적이 있다.
- **"심각도 낮음"도 재검토한다.** 데이터가 깨지지 않아도 요청이 유실되거나 테스트가 간헐적으로 실패하면 낮음이 아니다.
- 에이전트가 제안한 락 모드는 그대로 쓰지 않는다. 다른 정상 경로(예: `like_count` UPDATE)와 충돌하는지 PostgreSQL 락 충돌 표로 확인한다. `FOR SHARE`는 충돌해서 쓰지 않는다.

## 3. 재현: 테스트가 먼저
- 실패하는 테스트를 먼저 쓰고, 고치기 전 코드에서 실패하는 것을 확인한다.
- `sleep`을 쓰지 않는다. `LockProbe`로 별도 커넥션이 락을 쥔 채 대기시키고, `pg_stat_activity`의 `Lock` 대기를 폴링해 순서를 결정적으로 만든다.
- 락 때문에 막히는 지점이 없는 확인 후 실행 문제는 스파이로 중간에 다른 트랜잭션의 커밋을 끼워 넣는다.

## 4. 수정과 기록
- 변경 요약을 제시하고 승인받은 뒤 고친다.
- 고친 코드를 되돌렸을 때 테스트가 실패하는지 확인한다.
- 락 선택 근거와 포기한 대안을 `docs/readme-decisions.md`에 남긴다.
